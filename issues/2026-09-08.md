## Existing rollout blocker and manual intervention

The `mshv` pool initially reported Updating, with zero of two machines updated
and one unavailable. The pool wanted
`rendered-mshv-bb6c6aaf6b1a1d0a4b36539bc539ce1b` (including `psi=1`), but both
nodes still had current and desired config
`rendered-mshv-654ae7eeb1456871e5606843d3f147b1` and MCD state `Done`.

Node `l7njd` was Ready but cordoned. Its `spec.unschedulable` managed-fields
entry identified manager `oc` at 2026-09-07 10:49:24 UTC. This exhausted the
pool's default `maxUnavailable=1` budget before the new config could be assigned.
There was no outstanding MCD drain request; current PDBs allowed disruptions.

The user confirmed that the cordon was from an unrelated scheduling test and
explicitly authorized removing it. Manual intervention:

```sh
oc --kubeconfig=./kubeconfig adm uncordon \
  aro-virt-test-8gpzs-worker-mshv-centralus1-l7njd
```

This removed the test-imposed scheduling restriction, allowing the existing
rollout to complete normally. It is not a product fix. No disruption budget,
drain policy, or MCD annotation was overridden.

## nokaslr deployment and verification

Ran the new opt-in target after the pool became Updated:

```sh
AZURE_CONFIG_DIR="$HOME/.azure-virt-test" \
KUBECONFIG="$PWD/kubeconfig" make mshv-nokaslr
```

The target applied `99-mshv-nokaslr`, selecting only MachineConfig role `mshv`,
and waited for the normal MCO rollout. Both nodes converged to
`rendered-mshv-2839f60209a997ea1c22926dcaacf609`. Final pool status:
Updated=True, Updating=False, Degraded=False, 2/2 machines ready and updated.
Both nodes were Ready and schedulable.

`oc debug` verified `/proc/cmdline` on each node contained:

```text
systemd.unified_cgroup_hierarchy=1 cgroup_no_v1=all psi=1 nokaslr
```

The boot image on both nodes remained the custom kernel
`6.12.0-211.49.1.1794_2798046552.el10_2.x86_64`. A second target execution
reported the MachineConfig unchanged and passed both host checks again.

Disabling KASLR is a requested diagnostic intervention that reduces kernel
exploit protection, not a fix for any validation failure. Userspace and guest
ASLR were not changed. No validation checkup was run as part of this change.

### Core analysis: libcrypto mapping beyond EOF

Preserved the `virtqemud` core from PID 102464 at 20:11:05 UTC, boot ID
`e5e4bc1f55f44e3984d171f602e6b09b`, and the exact container-image dynamic loader.
GDB's core register and mapping data show:

```text
signal: SIGBUS, si_code=2 (BUS_ADRERR)
RIP:    0x7f90404a478a = ld-linux-x86-64.so.2 + 0x2678a
RDI:    0x7f903eb35990 = fault address
RDX:    0x670

libcrypto mapping:
0x7f903eabc000-0x7f903eb36000, file offset 0x548000

fault file offset:
0x7f903eb35990 - 0x7f903eabc000 + 0x548000 = 0x5c1990
actual file length on bl5zw: 0x400000
```

Disassembly of the matching loader identifies the faulting instruction as
`memset+0x3a`:

```text
2678a: 0f 11 07    movups %xmm0,(%rdi)
```

The loader is writing into a libcrypto file-backed mapping beyond the truncated
file's end, explaining SIGBUS during startup. This is not a QEMU guest launch
failure or the earlier kernel `csum_partial` panic. HCO's truncated executables
strongly explain their exits within 7-9 milliseconds, before application logs;
no HCO core was found, so SIGSEGV there is inferred from exit 139 rather than
confirmed by core signal metadata.

That boot's last retained journal entry is at 12:34:02. The next boot starts at

storage, or another writer, nor establish why that earlier reboot occurred.
The failures predate the evening nokaslr rollout; they must not be attributed to
disabling KASLR solely because they were investigated afterward.

## Manual recovery: replace the affected worker

The user requested recovery and explicitly selected worker replacement after
inspection showed that the damaged base layer was shared by 22 cached CNV
images, including images used by running containers. A three-image repull would
not remove the shared damaged layer. No VM or PVC-backed pod was present on
`bl5zw`; its non-DaemonSet workloads were infrastructure pods and a debug session.

Before replacement, preserved the three truncated files and image/layer metadata
in `.checkup-runs/cnv-startup-20260908/damaged-image-evidence.tar.gz`, verified
the archive listing, and saved `machine-before-replacement.yaml`. This is a
targeted evidence archive, not a full disk snapshot. The user-authorized
replacement destroys the old worker's remaining local disk state.

Manual interventions around 21:02 UTC:

```sh
oc --kubeconfig=./kubeconfig adm drain \
  aro-virt-test-8gpzs-worker-mshv-centralus1-bl5zw \
  --ignore-daemonsets --delete-emptydir-data --force --timeout=10m
oc --kubeconfig=./kubeconfig delete machine \
  aro-virt-test-8gpzs-worker-mshv-centralus1-bl5zw \
  -n openshift-machine-api --wait=false
```

`--force` allowed eviction of the ownerless debug pod; it did not bypass PDBs.
Drain retried the template-validator and network-injector evictions until their
budgets permitted them. EmptyDir data was discarded. No disruption budgets,
MachineSet templates, image references, or host image files were altered.
ARO MachineSet reconciliation was verified disabled before replacement.

The first replacement, `n2jsk`, failed with Azure quota exceeded while the old
VM was still deleting (384/384 StandardDdsv6Family cores, another 192 requested).
After the old VM disappeared, controllers automatically retried with `7rn6g`;
no quota increase or manual failed-Machine cleanup was needed.

Replacement node `aro-virt-test-8gpzs-worker-mshv-centralus1-7rn6g` joined with
both `mshv` and `worker` role labels and converged normally to
`rendered-mshv-2839f60209a997ea1c22926dcaacf609`. Verified:

- Custom kernel `6.12.0-211.49.1.1794_2798046552.el10_2.x86_64`.
- `/proc/cmdline` includes `psi=1 nokaslr`.
- `/dev/mshv`, `/dev/vhost-net`, loaded `mshv_root`, and L1VH boot message.
- The formerly damaged base layer's `libcrypto.so.3.5.5` is 6,159,568 bytes,
  SHA-256 `285efd507107f64235c6412f9ba027a237db8951fad5f8b528ccd1a8a3d1482a`,
  matching the previous good-node comparison.
- Both workers Ready and schedulable; MSHV pool Updated, 2/2 ready and updated.
- HCO operator and webhook Running after rescheduling to `l7njd`.
- `virt-handler` DaemonSet 2/2 Ready and Available; no CNV pods unready at final check.
- CNV CSV `4.99.0-2981` Succeeded; HCO Available=True, Progressing=False,
  Degraded=False, Upgradeable=True. Existing TaintedConfiguration=True persists.
- All core ClusterOperators Available, not Progressing, and not Degraded.

The original CNV startup incident is **recovered through manual node
replacement**, not fixed at its underlying cause. File truncation remains open.
No validation checkup or networking reproducer was run during this recovery.
