# 2026-07-25 - QEMU 9.8.z validation reaches running VMIs but remains incomplete

## Summary

The OpenShift Virtualization validation checkup was run with a diagnostic
virt-launcher containing the Red Hat-signed
`qemu-kvm-10.1.0-17.el9_8.3` packages from `RHBA-2026:28656`.

The corrected QEMU no longer reproduced the original immediate MSHV failure:

```text
invalid intercept access type: execute
failed to handle mmio
Failed to run on vcpu 0
```

Validation VMIs repeatedly reached `Running`, and 34 completed compute specs
passed. However, most guest-dependent specs could not use the guest console or
guest agent. The most complete run reached 53 of 61 compute specs, with 34
passing and 19 failing, before the MSHV node restarted. Network and storage did
not start in that run.

An earlier run completed two failed network specs before the same node also
restarted. Neither run produced a complete three-suite result. The diagnostic
launcher addresses the immediate QEMU abort but does not establish broad MSHV
guest functionality or constitute a product fix.

## Run 20260725-011445

The checkup requested `compute,network,storage` with no user-supplied skips.

Compute's `SynchronizedBeforeSuite` failed because `kubevirt-test-default1`
already existed, then its cleanup removed the shared test namespaces. Compute
therefore ran zero specs; this was a suite setup collision rather than a
compute test verdict. The available artifacts do not identify which earlier
execution created the namespace.

Network recreated the test namespaces and completed two specs. Both failed
after three attempts because Alpine VMIs reached `Running` but console login
timed out with no matched output:

1. Primary pod network status without a guest agent.
2. Same-namespace network-policy connectivity, test `1513`.

A third network-policy spec created and started a VMI at approximately
`01:44:45Z`. The preserved log ends while attempting its console login. No
network JUnit file or storage directory was produced.

The Job annotations at their final update reported:

```text
compute: 0 / 61 completed, setup failed
network: 2 / 18 completed, 0 passed, 2 failed
storage: 0 / 62 completed
```

The Job pod subsequently became `ContainerStatusUnknown`, exit code `137`, and
the Job failed with `BackoffLimitExceeded`.

## Guest Runtime Evidence

Failed guest-dependent specs consistently showed that the control-plane and
launcher lifecycle progressed farther than with the shipped QEMU:

- VMI events reported `Created` and `Started`.
- VMI status reported `Running` and often `Ready=True`.
- The active launcher image was the diagnostic `.3` digest.
- Launcher logs identified `qemu-kvm-10.1.0-17.el9_8.3`.
- QEMU processes remained present instead of immediately exiting with signal
  `SIGABRT`.
- The original intercept/MMIO/vCPU failure strings were absent from the
  preserved validation logs.

The same artifacts commonly showed empty guest console logs, login timeouts,
or a missing guest-agent condition. A `Running` VMI therefore did not imply a
usable guest in these runs.


These transitions align with the two checkup pod failures. Both preceding
journals end abruptly during active validation without an orderly shutdown
sequence. No preserved panic, OOM kill, watchdog, machine check, Azure reboot
operation, or explicit reboot request identifies the cause.

The host repeatedly logged:

```text
enP30832s1 selects TX queue <N>, but real number of TX queues is 32
```

Selected queue numbers reached at least `190`, and thousands of visible
warnings were accompanied by `net_ratelimit` suppression notices. The warnings
were sustained during both validation periods. They are a separate open
finding; the available evidence does not prove that they caused guest console
failures or either node restart, or whether their source is QEMU, KubeVirt,
OVN, the Azure synthetic NIC, or the host kernel.

The host also continued to report:

```text
using unsupported MSHV_CREATE_PARTITION ioctl
```

This confirms that the host/driver path remains outside its validated host
range. It does not by itself explain the observed failures because it also
appeared during earlier direct probes that remained alive.

## Manual Interventions

No validation failure was manually skipped, filtered, or otherwise worked
around. The checkup automatically added its normal `!RequiresRWXBlock`
capability filter.

- After the earlier temporary VMI experiment had restored the shipped launcher,
  the unsupported diagnostic launcher override was applied persistently for
  full validation. This is a diagnostic intervention, not a product fix.
- A results-reader pod was created for run `20260725-011445` to mount the
  preserved PVC and extract partial artifacts.
- After preserving those artifacts, the four `kubevirt-test-*` namespaces left
  by the interrupted run were deleted so a clean rerun could initialize its
  normal test namespaces. This cleanup does not fix either the guest failures
  or node restarts.
- The unchanged three-suite validation was rerun once as `20260725-032300`.
- The same four orphaned test namespaces were deleted after preserving the
  second run's artifacts. The failed Job, PVC, and results reader remain for
  inspection.
- Read-only `oc debug node/...` sessions collected boot boundaries and the
  preceding journal from the MSHV node after each interruption.
- No third run was started after the same node restarted again.
- The diagnostic launcher was not restored after either failure.

## Conclusion

The signed QEMU `.3` build changes the primary failure mode: MSHV domains no
longer abort immediately and enough control-plane and lifecycle behavior works
for 34 compute specs to pass. Guest boot or guest communication remains
unreliable across Alpine and Fedora-based tests, and the only MSHV node
restarted twice during validation.

The result remains open and incomplete until the normal CNV-delivered launcher
contains the corrected QEMU and a full compute, network, and storage run can
finish without manual cleanup or node interruption.
