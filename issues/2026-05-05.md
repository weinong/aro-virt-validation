## Summary

The MSHV infrastructure setup now reaches a healthy non-test state, but only
after several manual interventions. The MSHV node is Ready on RHCOS 10,
`mshv_root` loads persistently after reboot, `/dev/mshv` and `/dev/vhost-net`
are present, and KubeVirt advertises the `devices.kubevirt.io/mshv` resource
after the HCO `hyperv-direct` patch.

Follow-up discussion clarified that the `MSHV_CREATE_PARTITION unsupported`
dmesg line is likely a red herring: it was intentionally added during the
RHCOS/CentOS Stream 10 `mshv_root` backport to taint/warn, while continuing
execution. It should not be treated as proof that partition creation is the root
cause. If a KubeVirt VM still fails to boot, the next likely area to investigate
is the KubeVirt/libvirt/QEMU launch path.

No validation tests were run in this pass.

Manual interventions in this report are not fixes for the underlying product or
declarative-path issues. They were used only to unblock infrastructure setup and
must remain tracked until the same state can be reached without manual edits,
direct object creation, or node annotations.

## Manual interventions used

These interventions unblocked the setup, but they are not fixes. Each item keeps
an underlying issue open because the normal declarative or product-managed path
did not reach the same state by itself.

1. Disabled ARO MachineSet reconciliation after cluster creation so the custom
   MSHV MachineSet would not be reverted.
   Reason: ARO-managed reconciliation is expected to preserve supported worker
   shapes, while this validation needs a custom `Standard_D192ds_v6` MSHV
   MachineSet with the L1VH placement tag.
   Open issue: the validation workflow still needs an explicit supported path
   for custom MSHV MachineSets on ARO.
2. Scaled `machine-api-operator` to `0` and removed
   `MachineAPIMigration=true` from `machine-api-controllers` before creating a
   direct Machine.
   Reason: the 4.22 controller repeatedly tried to use
   `.status.authoritativeAPI` on `MachineAPIMigration`, but the served CRD did
   not include that field, blocking MachineSet-based provisioning.
   Open issue: MachineSet provisioning remains blocked unless the 4.22
   `MachineAPIMigration` controller/CRD mismatch is fixed or avoided by a
   supported configuration.
3. Created the MSHV Machine directly under the MachineSet labels.
   Reason: MachineSet reconciliation was blocked, but Azure VM provisioning had
   to be validated for the MSHV SKU and L1VH placement tag.
   Open issue: direct Machine creation is not a replacement for working
   MachineSet reconciliation.
4. Removed the inherited `worker` role from the MSHV node.
   Reason: the node needed to be isolated for MSHV-specific configuration and
   scheduling.
   Open issue: the desired node-role ownership and interaction with the worker
   pool should be defined so the `mshv` pool can be managed declaratively.
5. Created manual rendered MachineConfigs and annotated the node to force
   `rendered-mshv-manual-rhcos10`, then
   `rendered-mshv-manual-rhcos10-mshvroot`.
   Reason: the `mshv` MCP stayed at `machineCount: 0` with empty configuration
   and did not render/apply the intended RHCOS 10 or module-load config.
   Open issue: the `mshv` MCP render/status path must be fixed so RHCOS 10 and
   `mshv_root` loading can be applied without manual rendered configs or node
   annotations.
6. Ran `modprobe mshv_root` once through `oc debug node/...`.
   Reason: this confirmed the module was present and created `/dev/mshv` before
   making the module-load change persistent.
   Open issue: this was only a diagnostic/manual load; persistent loading still
   needs to be delivered by a declarative MachineConfig path.
7. Applied the missing `dnsnameresolvers.network.openshift.io` CRD from the
   extracted 4.22.0-rc.2 release payload.
   Reason: OVN was configured with `enable-dns-name-resolver=true`, but the CRD
   was absent after enabling `TechPreviewNoUpgrade`, causing network readiness
   failures.
   Open issue: the feature-set transition should install or reconcile this CRD
   automatically when OVN depends on it.
8. Used the HCO `kubevirt.kubevirt.io/jsonpatch` annotation instead of a direct
   `spec.hypervisors` patch.
   Reason: the installed HCO webhook rejected a direct `spec.hypervisors` patch
   even though the CRD schema exposed hypervisor fields.
   Open issue: the supported API path for enabling `hyperv-direct` should be
   clarified or fixed so it does not require an unsupported-feature annotation.

#### Interpretation

The evidence rules out the common cluster-level causes for the earlier MSHV
validation failure:

```
MSHV node Ready:                  yes
RHCOS 10 kernel running:          yes
L1VH partition mode:              yes
/dev/mshv present:                yes
/dev/vhost-net present:           yes
mshv_root loaded after reboot:    yes
KubeVirt hyperv-direct enabled:   yes
virt-handler advertises mshv:     yes
Current VM/VMI workload present:  no
```

The previous hypothesis was that the remaining failure point was the kernel
rejecting `MSHV_CREATE_PARTITION`. Follow-up discussion indicates that hypothesis
is likely wrong: the warning can be emitted while execution continues. The module
still reports that the host build is outside its validation range:

```
current host build: 26102
module minimum:     27744
module maximum:     27751
```

That leaves these open questions rather than confirmed root causes:

1. Is the `mshv_root` validated range intentionally narrow, and what behavior is
   expected when the current host build is outside that range?
2. What exact taint/warning semantics are expected from the backported
   `MSHV_CREATE_PARTITION unsupported` log path?
3. If KubeVirt VM boot still fails, is the failure in KubeVirt, libvirt, QEMU,
   guest kernel direct boot, machine type selection, or downstream packaging?
4. Which QEMU/libvirt build is known to launch a basic MSHV guest on this node,
   and how does it differ from the KubeVirt virt-launcher payload?

#### Impact

The cluster is structurally ready for `hyperv-direct` validation, but readiness
does not prove guest boot correctness. Any validation result that only checks
node readiness, device presence, or KubeVirt resource advertisement can pass
