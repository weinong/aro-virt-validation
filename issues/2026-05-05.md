**MSHV node:** `<mshv-node>`

**Primary issue:** Azure Hyper-V host build is outside the RHCOS `mshv_root`

## Summary

The MSHV infrastructure setup now reaches a healthy non-test state. The MSHV
node is Ready on RHCOS 10, `mshv_root` loads persistently after reboot,
`/dev/mshv` and `/dev/vhost-net` are present, and KubeVirt advertises the
`devices.kubevirt.io/mshv` resource after the HCO `hyperv-direct` patch.

The remaining blocker appears below the Kubernetes/CNV configuration layer: the
RHCOS 10 `mshv_root` module reports that the Azure Hyper-V host build is not in
its validated range, and dmesg shows `MSHV_CREATE_PARTITION` ioctl rejection.
This is the kernel operation required to create an MSHV partition for a VM.

No validation tests were run in this pass.

### Hyper-V host build remains below mshv_root validation range

This is the primary remaining blocker. The cluster, node, HCO, KubeVirt, and
device-plugin layers are healthy, but the kernel module reports a host-side ABI
or validation mismatch.

The node is definitely running on Hyper-V and is in L1VH mode:

```

Hyper-V: Nested features: 0x0

The `mshv_root` module loads and creates `/dev/mshv`, but it immediately logs

```

The kernel then logs rejected partition creation ioctls:

This matches the earlier validation blocker documented on 2026-04-23, where VMIs
briefly transitioned through startup and then crashed. No validation tests were
run in this pass, and there are currently no VM or VMI resources in the cluster:

```

```

The ioctl evidence should therefore be treated as fresh kernel evidence that the
underlying host/kernel compatibility issue still exists, not as a fresh test run

#### Interpretation

The evidence rules out the common cluster-level causes for the earlier MSHV
validation failure:

```
MSHV node Ready:                  yes
RHCOS 10 kernel running:          yes
L1VH partition mode:              yes
/dev/mshv present:                yes
/dev/vhost-net present:           yes
mshv_root loaded after reboot:    yes
KubeVirt hyperv-direct enabled:   yes
virt-handler advertises mshv:     yes
Current VM/VMI workload present:  no
```

The remaining failure point is lower: the RHCOS kernel module is exposing
`/dev/mshv`, but when the MSHV partition creation path is exercised, it rejects
`MSHV_CREATE_PARTITION`. The module itself reports that the host build is outside
its validated range:

```
current host build: 26102
module minimum:     27744
module maximum:     27751
```

That points to one of these likely causes:

1. The Azure host build backing this `Standard_D192ds_v6` VM does not include the
   MSHV ABI level expected by this RHCOS 10.2 kernel module.
2. The RHCOS 10.2 `mshv_root` validation range is too narrow or stale for the
   Azure host build currently used in `centralus`.
3. The L1VH platform tag successfully places the VM in L1VH mode, but does not
   guarantee a host build that supports the MSHV partition ioctl expected by this
   kernel.
4. The `MSHV_CREATE_PARTITION` ioctl contract changed between Hyper-V host build
   `26102` and the `27744-27751` range targeted by this module.

#### Impact

This issue blocks meaningful `hyperv-direct` VM validation even though the
cluster appears structurally ready. Any validation result that only checks node
readiness, device presence, or KubeVirt resource advertisement can pass while VM
startup still fails at the kernel/hypervisor ioctl layer.

#### Escalation questions

1. Is Azure Hyper-V host build `10.0.26102.1277-1-0` expected to support
   `MSHV_CREATE_PARTITION` for L1VH guests?
2. Is the `mshv_root` module's validated range of `27744-27751` intentional for
   this RHCOS 10.2 build?
3. Should `Standard_D192ds_v6` with
   `platformsettings.host_environment.nodefeatures.hierarchicalvirtualizationv1=True`
   be scheduled onto a host build inside `27744-27751`?
4. If host build `26102` is expected in `centralus`, is a newer/different
   `mshv_root` module required?
5. Is there an Azure placement, host group, region, SKU, or tag requirement that
   guarantees the validated host build range for MSHV/L1VH validation?
