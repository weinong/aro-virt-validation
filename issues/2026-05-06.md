# ARO 4.22.0-rc.2 TechPreview extension blocker

**Date:** 2026-05-06
**Cluster:** `<cluster-name>`
**OCP version:** 4.22.0-rc.2
**Feature set:** TechPreviewNoUpgrade
**Status:** Blocked before MSHV node setup, CNV installation, HCO patching, and validation.

## Summary

A declarative rerun stopped after enabling `TechPreviewNoUpgrade`. The cluster did
not expose all extension APIs required by the 4.22 TechPreview payload. As a
result, ClusterVersion kept retrying a missing resource type, OVN degraded
because a TechPreview network CRD was absent, and the declarative MSHV path could
not verify the RHCOS 10 OS stream.

No manual payload CRDs were applied in this rerun. Per the stop-and-document
rules, this remains a product/declarative-path blocker rather than a fixed setup
step.

## Reproduction Flow

The rerun used the revised ordering:

1. Create a fresh base ARO cluster.
2. Upgrade sequentially to OCP `4.22.0-rc.2`.
3. Enable `TechPreviewNoUpgrade`.
4. Stop before MSHV node setup because the cluster did not settle.

CNV installation, HCO patching, and validation were intentionally deferred and
were not run.

## ClusterVersion Failure

After enabling `TechPreviewNoUpgrade`, ClusterVersion remained stuck applying
TechPreview-gated extension resources:

```text
ClusterVersion: Available=True Progressing=True Failing=True
Reason:         UpdatePayloadResourceTypeMissing
Message:        Could not update criocredentialproviderconfig "cluster":
                the server does not recognize this resource, check extension API servers
Missing CRD:    criocredentialproviderconfigs.config.openshift.io
```

The corresponding API was not served:

```text
Error from server (NotFound): customresourcedefinitions.apiextensions.k8s.io
"criocredentialproviderconfigs.config.openshift.io" not found
```

### Payload ordering evidence

The extracted `4.22.0-rc.2` release payload contains both the singleton
`CRIOCredentialProviderConfig` object and its CRD, but the object appears earlier
by manifest run-level/name than the CRD:

```text
0000_05_config-operator_02_criocredentialproviderconfig.cr.yaml
0000_10_config-operator_01_criocredentialproviderconfigs.crd.yaml
```

The singleton object is gated by the feature gate:

```yaml
apiVersion: config.openshift.io/v1alpha1
kind: CRIOCredentialProviderConfig
metadata:
  annotations:
    release.openshift.io/feature-gate: CRIOCredentialProviderConfig
  name: cluster
spec: {}
```

The matching CRD is gated by feature set:

```yaml
kind: CustomResourceDefinition
metadata:
  annotations:
    api.openshift.io/merged-by-featuregates: "true"
    release.openshift.io/feature-set: CustomNoUpgrade,DevPreviewNoUpgrade,TechPreviewNoUpgrade
  name: criocredentialproviderconfigs.config.openshift.io
```

This makes the failure look like a TechPreview-gated payload dependency/order
issue: CVO includes the feature-gated singleton after `TechPreviewNoUpgrade`
enables `CRIOCredentialProviderConfig`, but the feature-set-gated CRD is not
served when CVO reaches the singleton, so the update stops at `33 of 1084`.

## OVN Failure

The network operator degraded because OVN was launched with DNS name resolver
support enabled while the matching CRD was absent:

```text
OVN flag:    --enable-dns-name-resolver
Missing CRD: dnsnameresolvers.network.openshift.io
OVN error:   failed to start cluster manager: error in syncing cache for
             *v1alpha1.DNSNameResolver informer
```

The corresponding API was not served:

```text
Error from server (NotFound): customresourcedefinitions.apiextensions.k8s.io
"dnsnameresolvers.network.openshift.io" not found
```

Pods scheduled to one control-plane node then failed pod sandbox creation because
that node had no CNI configuration:

```text
FailedCreatePodSandBox: no CNI configuration file in /etc/kubernetes/cni/net.d/.
Has your network provider started?
```

Observed operator impact included degraded `network`, `kube-apiserver`,
`openshift-apiserver`, and `authentication` operators.

## Missing OSImageStream API

The expected `OSImageStream/cluster` API was also absent, so the declarative MSHV
path could not verify the `rhel-10` stream:

```text
Missing CRD/API: osimagestreams.machineconfiguration.openshift.io
```

The currently served machine-configuration APIs included `machineosbuilds` and
`machineosconfigs`, but not `osimagestreams`.

## Manual Interventions

No manual interventions were applied for this rerun.

The previous historical run manually applied the DNSNameResolver CRD from the
release payload, which unblocked OVN in that run. That manual payload application
is not a fix and was intentionally not repeated here.

## Impact

The validation workflow cannot proceed through the normal declarative path until
the TechPreview transition installs or exposes the required extension APIs.

Blocked phases:

1. Declarative MSHV node setup.
2. CNV nightly installation.
3. HCO `hyperv-direct` patching.
4. Any CNV or VM validation.

## Expected Behavior

After enabling `TechPreviewNoUpgrade` on OCP `4.22.0-rc.2`, the cluster should
settle with `ClusterVersion Progressing=False` and should serve the extension
APIs required by enabled payload resources and operators, including:

```text
criocredentialproviderconfigs.config.openshift.io
dnsnameresolvers.network.openshift.io
osimagestreams.machineconfiguration.openshift.io
```

## Open Questions

1. Should `TechPreviewNoUpgrade` install these extension CRDs automatically on
   ARO `4.22.0-rc.2`?
2. Is `CRIOCredentialProviderConfig` expected to be gated differently from the
   resource payload that CVO applies?
3. Should OVN avoid enabling DNSNameResolver until the CRD is served?
4. Is `OSImageStream` still the intended API for declarative RHCOS 10 stream
   selection in this payload, or should the workflow target a different API?

## Next Steps

1. Track this as a blocker for the normal TechPreview/declarative path.
2. Do not apply payload CRDs manually unless explicitly documenting that action as
   a manual intervention.
3. Do not enable `TechPreviewNoUpgrade` on `4.22.0-rc.2` or older 4.22
   pre-release payloads in the normal validation flow; upgrade to a newer 4.22
   payload first.
4. Retry MSHV setup only after ClusterVersion and ClusterOperators settle and the
   required APIs are served.

## Automation Guard

The normal validation workflow now blocks `4.22.0-rc.2` and older 4.22
pre-release payloads at multiple points. This prevents the workflow from
re-entering the known CR-before-CRD failure.

`scripts/00-prereqs.sh` checks `TARGET_OCP_VERSION` before Azure resources are
created:

```sh
TARGET_OCP_VERSION=<newer-4.22-version> ./scripts/00-prereqs.sh
```

`scripts/02-upgrade-cluster.sh 4.22` refuses to select a known-bad target if the
candidate graph still offers one. `scripts/03-techpreview-setup.sh` keeps the
same guard immediately before enabling `TechPreviewNoUpgrade`.

The guard can be bypassed only for deliberate reproduction or investigation:

```sh
ALLOW_KNOWN_BAD_TECHPREVIEW_PAYLOAD=true ./scripts/03-techpreview-setup.sh
```
