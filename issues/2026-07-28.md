# 2026-07-28 - MSHV guest login failure localizes to CPU feature exposure

## Summary

OpenShift Virtualization compute test `1463` was reproduced in isolation with
the unchanged validation image and diagnostic QEMU `.3` launcher. All three
attempts reached the test's VMI-running condition, then timed out waiting for
an Alpine console login. The first attempt inspected live also reported
`Ready=True`.

Live QMP inspection showed that these VMIs were not booted guests with a broken
console. The only vCPU consumed approximately 65% CPU while its instruction
pointer remained fixed at a SeaBIOS `wrmsr` instruction for
`IA32_FEATURE_CONTROL` (`MSR 0x3a`). The serial log remained empty, the guest
agent stayed disconnected, and QEMU reported zero block reads. The VM had not
reached its boot disk.

A controlled CPU A/B showed that nested-VMX exposure and the tested SGX feature
combination are independent sufficient triggers for the firmware stall in this
configuration. Explicit CPU models without those features reached the Alpine
ISOLINUX bootloader. This provides a concrete explanation for the difference
between the earlier Westmere diagnostic VMI and this `host-model` reproduction.
It does not identify whether MSHV, QEMU, libvirt capability generation, or
another layer is responsible for the non-retiring MSR write.

This is a diagnostic result, not a test workaround or product fix. No validation
test or cluster CPU configuration was changed.

## Live Failure State

The first attempt, which was inspected live, used VMI `testvmi-txhzt-...` and
resolved `host-model` to:

```text
-cpu EPYC-Turin,...,vmx=on,...,sgx=on,...,sgx1=on,sgx2=on,...
```

KubeVirt and libvirt reported:

```text
VMI phase:       Running
VMI Ready:       True
libvirt state:   running (booted)
QMP query-status: running=true
serial log:      0 bytes
guest agent:     disconnected
block reads:     0 requests, 0 bytes
```

Three register samples over approximately twelve seconds were identical. `EDX`
was zero, so the complete `EDX:EAX` value is represented by `EAX` below:

```text
EIP=06fee26a
ECX=0000003a
EAX=00060005
```

Disassembly at that address showed:

```text
0x06fee26a: wrmsr
```

The QEMU thread named `CPU 0/MSHV` consumed approximately 68% CPU, while all
three samples remained at the same instruction. This proves that the vCPU did
not retire the `wrmsr` during the observation window. The value `0x60005`
contains the lock bit, VMX-outside-SMX enable, SGX global enable, and SGX Launch
Control enable bits.

The empty console and offline guest agent are therefore downstream symptoms of
an early firmware vCPU stall, not evidence of a console proxy or guest-agent
transport failure.

## CPU Capability Mismatch

The RHCOS host reports an Intel physical CPU:

```text
Vendor ID:       GenuineIntel
Model name:      INTEL(R) XEON(R) PLATINUM 8573C
```

The same launcher's libvirt `hyperv` domain capabilities report:

```xml
<mode name='host-model' supported='yes'>
  <model fallback='forbid'>EPYC-Turin</model>
  <vendor>AMD</vendor>
  ...
</mode>
```

That host model includes a very broad mixed-vendor feature list, including
VMX, SGX, Intel PT, and AMD SVM-related features. KubeVirt publishes the same
physical-host/domain-capability inconsistency on the node:

```text
cpu-vendor.node.kubevirt.io/AMD=true
host-model-cpu.node.kubevirt.io/EPYC-Turin=true
host-model-required-features.node.kubevirt.io/vmx=true
host-model-required-features.node.kubevirt.io/sgx=true
```

The meaning and source of this host-model result remain open. The evidence
shows that the validation test consumes the QEMU/libvirt capabilities through
KubeVirt node labels; it does not establish which layer generated an incorrect
value or whether every advertised feature is invalid.

## Diagnostic A/B Matrix

All controls used the same node, MSHV accelerator, QEMU `.3` launcher, q35
machine type, 128 MiB memory, virtio disk, and Alpine image.

| CPU definition | Result |
|---|---|
| `Westmere` | Reached ISOLINUX |
| `EPYC-Turin` | Reached ISOLINUX |
| `EPYC-Turin,vmx=on` | Stuck at `wrmsr MSR 0x3a`, value `0x5`; zero disk reads |
| `Westmere,vmx=on` | Stuck at `wrmsr MSR 0x3a`, value `0x5`; zero disk reads |
| `EPYC-Turin,sgx=on,sgx1=on,sgx2=on` | Stuck at `wrmsr MSR 0x3a`, value `0x40001`; zero disk reads |
| `host-passthrough` | Stuck at `wrmsr MSR 0x3a`, value `0x60005`; zero disk reads |
| `host-model,vmx=off` | Still stuck; SGX controls produced value `0x60001` |
| `host-model,vmx=off,sgx*=off` | Reached ISOLINUX |

The matrix demonstrates:

1. The base `EPYC-Turin` model is not sufficient to cause the stall.
2. Exposing `vmx` is sufficient, independent of whether the base model is Intel
   Westmere or AMD EPYC-Turin.
3. Exposing the tested `sgx+sgx1+sgx2` combination is independently sufficient.
4. Removing both top-level VMX and SGX exposure lets the otherwise expanded
   host model reach the bootloader.

The remaining nested-VMX subfeatures were still present in the positive
`host-model,vmx=off,sgx*=off` command. SeaBIOS did not enter the failing
`IA32_FEATURE_CONTROL` path because the top-level capabilities were disabled.

## Relationship to Earlier Failures

This finding provides a tested mechanism consistent with the repeated pattern
from the July 25 run:

- VMI `Running` and often `Ready=True`.
- QEMU process remains alive.
- Empty guest console.
- Guest agent never connects.
- Guest-dependent tests time out before their named assertion.

The earlier VMIs were not inspected at the register and block-I/O level, so the
same mechanism is not proven for every prior failure. Migration destination
constraints and the separate host TX-queue warnings remain independent open
findings. This result also does not prove the cause of the two earlier node
restarts.

## Manual Diagnostic Interventions

- Ran the unmodified validation test with a focus expression selecting only
  test `1463`. This was a diagnostic reproduction and not a replacement
  validation result.
- Used read-only `virsh` and QMP queries inside the failing launcher pod.
- Created temporary A/B VMIs with explicit CPU definitions.
- The CPU-feature-disabled VMIs were diagnostic controls only. No validation
  test was modified or rerun with those settings, and they are not described as
  fixes.
- Deleted the temporary A/B namespace and reader pod after preserving evidence.
- The persistent unsupported launcher override, previously applied through the
  CNV CSV/virt-operator and HCO pull-secret path because the shipped QEMU
  immediately aborts on MSHV, remained active and unchanged.

## Conclusion

For focused test `1463`, the guest-console timeout occurs because firmware does
not progress past an `IA32_FEATURE_CONTROL` write, not because the console
channel fails. In this configuration, VMX exposure or the tested SGX feature
combination is sufficient to reproduce the non-retiring write before any
boot-disk I/O. The normal `host-model` and `host-passthrough` paths expose those
features and reproduce the stall.

The responsible implementation layer remains open. A product resolution must
make normal CPU selection boot reliably under MSHV without per-VMI diagnostic
feature overrides.
