# 2026-07-14 - Phase 3 TechPreviewNoUpgrade fails on OCP 4.22.4

## Summary

The ARO end-to-end OpenShift Virtualization validation flow reached exact OCP
`4.22.4`, but stopped during `make techpreview`. Enabling
`TechPreviewNoUpgrade` caused Cluster Version Operator (CVO) to reapply the
`4.22.4` payload with the TechPreview feature gates enabled. CVO then attempted
to apply `CRIOCredentialProviderConfig/cluster` before the corresponding CRD was
served.

This is the same CR-before-CRD payload ordering failure previously documented
for `4.22.0-rc.3` and `4.22.0-rc.5`, now reproduced on GA `4.22.4`.

## Reproduction Flow

The existing ARO cluster was logged into with the repository kubeconfig. Its
state was verified before changes: OCP `4.20.15`, all ClusterOperators
`Available=True` and `Degraded=False`, both MCPs updated, default feature gates,
and no CNV or MSHV resources.

The flow then ran:

```sh
RESOURCEGROUP=aro-virt-test-rg CLUSTER=aro-virt-test \
  KUBECONFIG="$PWD/kubeconfig" make aro-disable-machineset-reconcile

RESOURCEGROUP=aro-virt-test-rg CLUSTER=aro-virt-test LOCATION=centralus \
  KUBECONFIG="$PWD/kubeconfig" make upgrade-to-4.22.4

KUBECONFIG="$PWD/kubeconfig" make techpreview
```

The first upgrade invocation completed `4.20.15` -> `4.21.24` and stopped before
starting `4.22.4` because the Azure CLI default subscription changed during the
long-running command. The safety check could not resolve the ARO API URL and
refused to proceed. After restoring the required `L1VH Virt Testing`
subscription, the pending hop was resumed with:

```sh
RESOURCEGROUP=aro-virt-test-rg CLUSTER=aro-virt-test LOCATION=centralus \
  KUBECONFIG="$PWD/kubeconfig" ./scripts/02-upgrade-cluster.sh 4.22.4
```

Both upgrade hops completed normally. All ClusterOperators were available and
not degraded, and both MCPs were updated before `make techpreview` began.

## Primary Failure

The first `make techpreview` invocation patched the feature set, waited for the
operators and MCPs, then checked for the required extension CRDs before CVO had
finished restarting and reapplying the payload. It stopped because the CRDs
were absent. No CRD was applied manually.

CVO then began the normal feature-gate payload reconciliation and persistently
stopped at item 33 of 1085:

```text
Running sync for criocredentialproviderconfig "cluster" (33 of 1085)
error running apply for criocredentialproviderconfig "cluster" (33 of 1085):
failed to get resource type: no matches for kind
"CRIOCredentialProviderConfig" in version "config.openshift.io/v1alpha1"
```

The FeatureGate status confirms that the relevant gates are enabled for
`4.22.4`:

```text
CRIOCredentialProviderConfig
DNSNameResolver
OSStreams
```

However, all three corresponding extension CRDs are absent:

```text
criocredentialproviderconfigs.config.openshift.io: NotFound
dnsnameresolvers.network.openshift.io: NotFound
osimagestreams.machineconfiguration.openshift.io: NotFound
```

The extracted `4.22.4` payload contains both resources, but names the custom
resource at an earlier run level than the CRD:

```text
0000_05_config-operator_02_criocredentialproviderconfig.cr.yaml
  apiVersion: config.openshift.io/v1alpha1
  kind: CRIOCredentialProviderConfig
  metadata:
    name: cluster
    annotations:
      release.openshift.io/create-only: "true"
      release.openshift.io/feature-gate: CRIOCredentialProviderConfig

0000_10_config-operator_01_criocredentialproviderconfigs.crd.yaml
  apiVersion: apiextensions.k8s.io/v1
  kind: CustomResourceDefinition
  metadata:
    name: criocredentialproviderconfigs.config.openshift.io
    annotations:
      api.openshift.io/merged-by-featuregates: "true"
      release.openshift.io/feature-set: CustomNoUpgrade,DevPreviewNoUpgrade,TechPreviewNoUpgrade
```

This ordering explains why CVO selects and applies the gated singleton at item
33 before the API server can discover the CRD at the later run level.

CVO remains at:

```text
Available=True
Progressing=True
Progressing message: Working towards 4.22.4: 32 of 1085 done (2% complete)
Failing reason: UpdatePayloadResourceTypeMissing
Failing message: Could not update criocredentialproviderconfig "cluster"
  (33 of 1085): the server does not recognize this resource, check extension
  API servers
```

The failure is therefore not a delayed operator or MCP rollout. CVO cannot
advance past the TechPreview-gated custom resource to reach the CRD later in
the payload.

## Current Cluster State

- OCP history records `4.22.4` as completed before the feature-set transition.
- `featuregate/cluster.spec.featureSet=TechPreviewNoUpgrade` is set and is
  irreversible.
- CVO is stuck reapplying `4.22.4` at item 33 of 1085.
- All ClusterOperators report `Available=True`, `Progressing=False`, and
  `Degraded=False` independently of the CVO payload-level failure.
- `master` and `worker` MCPs report `Updated=True`, `Updating=False`, and
  `Degraded=False`.
- All six base nodes remain `Ready`.
- No `mshv` MCP or MSHV MachineSet was created.
- The `openshift-cnv` and `ocp-virt-validation` namespaces do not exist.
- CNV `4.99` was not installed and the validation checkup did not run.

## Required Setup Action

ARO MachineSet reconciliation was explicitly disabled before custom MSHV work:

```sh
oc patch cluster.aro.openshift.io cluster --type=merge \
  -p '{"spec":{"operatorflags":{"aro.machineset.enabled":"false"}}}'
```

This is a required setup action for recreated ARO validation clusters. It is
not a fix or workaround for the CVO payload ordering failure.

## Manual Interventions and Workarounds

No missing CRDs, custom resources, MachineConfigs, Machines, MachineSets, or
node labels were manually applied or edited. The Azure CLI subscription was
restored to the repository-required subscription after the safety check stopped
the command; this changed only the local Azure CLI context and did not alter
cluster payload resources.

The failed validation was not worked around. In particular, the missing CRDs
were not extracted or hand-applied from the payload.

## Impact

The end-to-end OpenShift Virtualization validation cannot proceed through the
normal declarative path on this cluster. Blocked phases are:

1. Completion of `TechPreviewNoUpgrade` payload reconciliation.
2. Creation of the RHCOS 10 MSHV MachineConfigPool and MSHV MachineSet.
3. Installation of nightly CNV `4.99`.
4. HCO `hyperv-direct` configuration.
5. Execution of `ocp-virt-validation-checkup` compute, network, and storage
   suites.

## Verdict

OCP `4.22.4` still contains the TechPreview CR-before-CRD ordering defect seen
in earlier `4.22.0` release candidates. The issue remains open because the
normal payload path does not install and serve the required extension APIs.

The validation flow must continue to stop and document this condition rather
than applying the missing CRDs manually.

## Next Steps

1. File or update the upstream 4.22 CVO/config extensions issue with this GA
   `4.22.4` reproduction and the item `33 of 1085` log evidence.
2. Verify whether a newer payload, such as `4.22.5`, corrects the ordering on a
   newly created validation cluster. The current cluster cannot return from
   `TechPreviewNoUpgrade`.
3. Do not proceed with MSHV, CNV, HCO, or validation-checkup phases on this
   cluster unless the payload reconciles through the normal product path.
