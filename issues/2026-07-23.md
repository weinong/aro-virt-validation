# 2026-07-23 - OCP 4.22.7 validation reaches QEMU but MSHV guests crash

## Summary

The self-managed OCP path successfully created a healthy OCP 4.22.7 cluster,
enabled `TechPreviewNoUpgrade`, provisioned a declarative RHCOS 10 MSHV node,
installed CNV nightly `4.99.0-2921`, configured `hyperv-direct`, and started the
OpenShift Virtualization validation checkup.

After correcting three setup automation defects, the checkup passed its
`SynchronizedBeforeSuite` hypervisor check and began compute specs. VM domains
repeatedly started with `-accel mshv`, briefly entered `Running`, and then
crashed. A representative QEMU log reports:

```text
qemu-kvm: invalid intercept access type: execute
qemu-kvm: failed to handle mmio
qemu-kvm: Failed to run on vcpu 0
shutting down, reason=crashed
```

The host kernel reports `using unsupported MSHV_CREATE_PARTITION ioctl` for
launch attempts. The Azure host build is `26102`, while the RHCOS 10
`mshv_root` driver reports a validated range of `27744-27751`.

The three-suite checkup run was configured for compute, network, and storage
with no user-supplied skips. Its local two-hour timeout expired while compute
was still running.
At that boundary, the raw log contained 3 passing specs, 13 failed specs, and
one flaky spec that passed on retry. Network and storage had not started. The
checkup also added its automatic `!RequiresRWXBlock` capability filter because
RWX block storage was not configured; no user-supplied skip was used.

## Setup Automation Findings

### TechPreview synchronization race

The first `make techpreview` invocation patched the FeatureGate and immediately
observed the old `ClusterVersion Progressing=False` status before CVO began the
TechPreview payload reconciliation. It then failed because the required CRDs
were not yet present.

A later invocation observed transient CVO errors while newly created extension
APIs became served:

```text
Could not update clusterapi "cluster" (239 of 1085): the server does not recognize this resource
Could not update criocredentialproviderconfig "cluster" (33 of 1085): the server does not recognize this resource
```

No CRDs or custom resources were manually installed. CVO and the extension
operators reconciled normally, all required CRDs became established, CVO
cleared `Failing`, and the idempotent phase subsequently passed. OCP 4.22.7
therefore does not reproduce the persistent CR-before-CRD deadlock seen on the
earlier 4.22 payloads, but the phase script can report a premature failure.

### Incorrect MSHV worker-role rejection

The first `make mshv-node` invocation stopped because the MSHV node had both
`mshv` and `worker` roles. This was a repository validation defect. OCP 4.22
custom MachineConfigPool documentation requires the worker role plus the custom
role, and the custom pool itself selects MachineConfigs with both roles.

The rendered MSHV config installs kubelet with:

```text
--node-labels=node-role.kubernetes.io/worker,...
```

Commit `7f8bcb2` corrected the script to explicitly set and require both roles.
No node label was manually removed or added.

### Host probe false failure under pipefail

After the role correction, all host requirements were present, but phase 4
still failed because `lsmod | grep -q` and `dmesg | grep -q` ran under
`set -o pipefail`. A successful early `grep -q` exit can cause the producer to
receive SIGPIPE and make the whole pipeline nonzero.

Commit `2a820df` changed the probes to read `/proc/modules` directly and fully
drain the `dmesg` fallback. The phase then passed without changing host state.

### Missing HCO workload placement

The first validation run failed setup in all three suites with:

```text
Both mshv and vhost-net devices are required for testing, but are not present on cluster nodes
Ran 0 of 1401 Specs
```

Run artifacts:

```text
.checkup-runs/20260723-185220/
```

KubeVirt's `EnsureHypervisorPresent()` checks every node running virt-handler.
With global `hyperv-direct`, virt-handler initially ran on both the regular
worker and the MSHV worker. The regular worker correctly had no MSHV device, so
the cluster-wide precondition failed.

OpenShift Virtualization supports restricting workload components through HCO
node placement. Commit `360d46c` added the normal declarative configuration:

```yaml
spec:
  deployment:
    nodePlacements:
      workload:
        nodeSelector:
          node-role.kubernetes.io/mshv: ""
```

HCO propagated this to KubeVirt and the virt-handler DaemonSet. The final
DaemonSet had one desired and ready pod on the MSHV node only. This is an
environment configuration correction, not a test skip or a direct operand
patch.

## Ad-hoc MSHV Isolation Tests

Additional manual diagnostic workloads were run in a separate `adhoc-mshv`
namespace while the original validation Job continued unchanged. These probes
were not fixes and were not applied to the validation suite. Every diagnostic
resource and the namespace were deleted after evidence collection.

Artifacts are under:

```text
.smoke-runs/20260723T-adhoc-mshv/
```

### CPU model does not prevent the BIOS-path crash

Serial CirrOS VMI probes compared KubeVirt's default host model with two much
smaller CPU models advertised by the node:

| CPU model | Machine | Result |
|---|---|---|
| `EPYC-Turin` host model | `pc-q35-rhel9.8.0` | Crashed |
| `Westmere` | `pc-q35-rhel9.8.0` | Crashed |
| `Nehalem` | `pc-q35-rhel9.8.0` | Crashed |

All three entered `Running` for approximately one second and emitted the same
sequence:

```text
attempt to map region [...], while [...] is already mapped in the guest
invalid intercept access type: execute
failed to handle mmio
Failed to run on vcpu 0
```

This rules out the large `EPYC-Turin` feature expansion as a necessary
condition for the immediate legacy-BIOS crash.

### Removing guest devices does not prevent the crash

A `Westmere` VMI with no disk, network interface, RNG, graphics, input, or
serial console still failed at first vCPU execution with the same signature.
Its single launch increased the host's
`unsupported MSHV_CREATE_PARTITION ioctl` count from 145 to 147.

### The fault occurs when the vCPU begins execution

A `Westmere`/q35 VMI with `startStrategy: Paused` reached `Running` with
`Paused=True` and remained stable for ten seconds. After a real
`virtctl unpause` request:

```text
22:24:29 phase=Running paused=
22:24:31 phase=Failed paused=
```

Launcher timing further narrows the failure:

```text
22:24:28.631 qemu-kvm: invalid intercept access type: execute
22:24:28.631 qemu-kvm: failed to handle mmio
22:24:28.631 qemu-kvm: Failed to run on vcpu 0
22:24:28.637 Domain event="resumed" detail="unpaused"
22:24:29.343 Domain event="stopped" detail="failed"
```

The mapped-region warning was already present while the domain was paused; the
execute-intercept failure appeared only when the vCPU was unpaused.

### Direct QEMU reproduces without KubeVirt or libvirt lifecycle control

The exact CNV virt-launcher image was run in a restricted diagnostic pod with
`devices.kubevirt.io/mshv=1`. QEMU was invoked directly:

```text
/usr/libexec/qemu-kvm -machine q35,accel=mshv -cpu Westmere \
  -m 128 -smp 1 -nodefaults -display none
```

Results:

| Direct QEMU control | Result |
|---|---|
| MSHV q35 with `-S` | Stayed alive until the 10-second timeout (`124`) |
| MSHV q35, active vCPU | Aborted and dumped core (`134`) |
| MSHV i440fx, active vCPU | Aborted with the same intercept/MMIO error (`134`) |
| TCG q35, active vCPU | Stayed alive until the 10-second timeout (`124`) |

This reproduces the failure below KubeVirt and libvirt orchestration and makes
MSHV vCPU execution, rather than the VMI controller path, the differentiating
factor. The host recorded multiple `/usr/libexec/qemu-kvm` `SIGABRT` cores in
`systemd-coredump`.

The exact userspace packages were:

```text
qemu-kvm-core-10.1.0-17.el9_8.x86_64
libvirt-daemon-driver-qemu-11.10.0-12.3.el9_8.x86_64
libvirt-libs-11.10.0-12.3.el9_8.x86_64
```

The exact kernel module was:

```text
/lib/modules/6.12.0-211.34.1.el10_2.x86_64/kernel/drivers/hv/mshv_root.ko.xz
srcversion: 4458C8AC6F441988CAA8200
vermagic: 6.12.0-211.34.1.el10_2.x86_64 SMP preempt mod_unload modversions
```

### Partition warning is not sufficient to predict an abort

Controlled direct-QEMU launches incremented the host warning count once for
both a paused MSHV process and an active-vCPU MSHV process:

```text
before=167
after_paused=168
after_running=169
```

The paused process remained healthy until intentionally terminated. Therefore,
`unsupported MSHV_CREATE_PARTITION ioctl` confirms use of an unvalidated
compatibility path, but the warning alone is not sufficient to prove or predict
the later QEMU abort.

### UEFI changes the failure mode but is not a demonstrated fix

Direct QEMU with OVMF, q35, MSHV, and `Westmere` stayed active. A QMP query
after five seconds returned:

```json
{"return":{"status":"running","running":true}}
```

A KubeVirt CirrOS VMI and a Fedora test-tooling VMI configured with EFI and
secure boot disabled also remained in `Running` for 30 and 90 seconds,
respectively. Neither produced guest console output or reached
`AgentConnected=True`, so these probes do not establish that a guest OS booted.

The CPU model still matters on this alternate firmware path: direct QEMU with
OVMF and `EPYC-Turin` progressed beyond the legacy execute-intercept failure,
but later aborted with:

```text
Failed to translate gva (...) to gpa
failed to translate gva to gpa
failed to fetch instruction
```

EFI is therefore an actionable product-side investigation direction, not a
validated workaround or fix for the normal BIOS-based validation workloads.

## Manual Interventions and Workarounds

No product or test failure was worked around.

- No payload CRD or custom resource was manually installed.
- No direct Machine was created.
- No rendered MachineConfig was created manually.
- No node desired-config annotation was edited.
- No node role label was manually changed.
- No operator was scaled down or directly patched.
- No KubeVirt operand or virt-handler DaemonSet was directly patched.
- No validation test was manually skipped, filtered, or modified. The checkup
  automatically added its normal `!RequiresRWXBlock` capability filter.

The HCO workload node placement is the supported declarative configuration for
restricting virtualization workload components to capable nodes. The repeated
phase invocations were idempotent reruns after normal controller reconciliation
or committed setup-script corrections.

Read-only `oc debug node/...` commands were used to collect host evidence.

## Verdict

The OCP 4.22.7 declarative environment path is functional through CNV and HCO
once the repository automation defects are corrected. The validation suite can
discover MSHV and start compute tests.

The environment is not functional for guest workloads. QEMU uses `-accel mshv`
as intended, but guests crash on vCPU 0 while the unvalidated host/driver
combination emits the unsupported partition ioctl warning. The precise causal
layer remains open. No test or cluster workaround was applied.
