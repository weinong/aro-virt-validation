# 2026-05-09 — Smoke VM crashes inside MSHV accelerator on RHCOS 10 / CNV 4.99 nightly

## Summary

A minimum-spec cirros VMI scheduled to the MSHV node reached `phase: Running`
for ~1 second and then **crashed inside QEMU on vcpu 0**. The MSHV path is
wired up correctly end-to-end (KubeVirt selects `-accel mshv`, `/dev/mshv` is
exposed via the device plugin and cgroups), but the accelerator itself rejects
an intercept produced by the auto-generated `EPYC-Turin` host-model CPU
description, and the host kernel logs `using unsupported MSHV_CREATE_PARTITION
ioctl` for every launch.

Per `AGENTS.md`, manual interventions and one-off workarounds must not be
described as fixes; underlying product issues stay open until the normal
declarative path works on its own. Following that rule, the
`using unsupported MSHV_CREATE_PARTITION ioctl` host-kernel message is
treated as **suggestive only**; the QEMU `invalid intercept access type:
execute` / `failed to handle mmio` on vcpu 0 is the corroborating VM-side
evidence that promotes this from "noisy log line" to a real product issue.

### Host kernel (RHCOS 10 mshv node)

```text
[   12.276068] misc mshv: Running on unvalidated Hyper-V version
[   12.276820] misc mshv: Versions: current: 26102  min: 27744  max: 27751
[ 1815.813553] using unsupported MSHV_CREATE_PARTITION ioctl
[ 1911.119854]  ? exc_page_fault+0x7f/0x150
[ 1925.x ...   ] using unsupported MSHV_CREATE_PARTITION ioctl
[ 2627.217198] using unsupported MSHV_CREATE_PARTITION ioctl
[ 2628.113894] using unsupported MSHV_CREATE_PARTITION ioctl
```

The MSHV kernel driver itself reports the running Hyper-V version is **older**
than the minimum the driver was built against (`current: 26102` vs
`min: 27744`), and downgrades to "unsupported ioctl" handling for
`MSHV_CREATE_PARTITION` whenever a VM is launched. The
`using unsupported MSHV_CREATE_PARTITION ioctl` line was observed during
multiple VM-launch attempts on this node (the smoke VMI documented here was
one of several short-lived launches). The single page-fault oops at
`[1911.119854]` is captured for completeness but the captured `dmesg` does
not, on its own, prove a direct causal link between that oops and this
specific VMI's lifetime — it falls in the same general window
(`+1815s`–`+2628s` since boot) but the boot-relative timestamps cannot be
mapped to wall-clock `20:42:32Z` precisely from the artifacts here.

## Suspected root cause

Two stacked product issues, both on the MSHV side:

1. **Azure L1VH host Hyper-V build is older than the RHCOS 10
   `mshv_root.ko` requires.** The driver explicitly advertises
   `min: 27744 max: 27751` and we are on `26102`. The "unsupported
   MSHV_CREATE_PARTITION ioctl" message is a direct consequence — the
   driver silently falls back to a degraded path for the partition-create
   call instead of refusing the ioctl outright.

2. **QEMU's MSHV accelerator does not implement an intercept produced by
   the auto-generated host-model `EPYC-Turin` CPU description.** Even with
   the correct accelerator selected and the device exposed, vcpu 0 traps
   on `invalid intercept access type: execute` immediately after boot.

Whether (2) is independent or downstream of (1) cannot be determined from
the captured artifacts alone — both need product-side investigation.

## What was *not* tried (and is left as next steps, not workarounds)

- Explicitly pinning a much smaller `spec.domain.cpu.model` (e.g.
  `Westmere`, `Nehalem`, or `qemu64`) in the VMI to bypass the giant
  `EPYC-Turin` feature surface. The repo's `AGENTS.md` and
  `issues/2026-04-23.md` already call out `cpuModel: qemu64-v1` as a
  workaround that introduces its own nodeSelector mismatch, so this is a
  diagnostic step, not a fix.
- Disabling the `WithHostModelCPU` feature gate on the KubeVirt CR.
- Re-trying with a Hyper-V build inside the documented
  `min/max` range supported by `mshv_root` in this kernel.

These are deliberately omitted so that the underlying product issue is
visible and not masked.

## Manual interventions performed (none yet for this issue)

No manual interventions have been applied to mitigate this crash. Phases 4–7
ran through the normal declarative path:

- `MachineConfigPool/mshv` with `spec.osImageStream.name: rhel-10`
- `MachineConfig/99-mshv-load-mshv-root` (persistent module-load)
- Worker-template-derived `MachineSet` with VM size `Standard_D192ds_v6`,
  L1VH placement tag, and `spec.template.spec.metadata.labels:
  node-role.kubernetes.io/mshv: ""`
- HCO annotated with the documented `kubevirt.kubevirt.io/jsonpatch`
  enabling `ConfigurableHypervisor` + `hypervisors=[{name:hyperv-direct}]`
  + `evictionStrategy: None`. **`cpuModel` deliberately not set.**

The two script edits committed on this branch
(`f64f031`: phase 4 self-managed/CAPI fix; `3c2f5aa`: phase 5 wait-all MCPs)
are infrastructure-script bugs, not workarounds for this VM crash.
