# 2026-05-29 - Phase 3 TechPreviewNoUpgrade fails on 4.22.0-rc.5

## Summary

Running `make techpreview` on the current ARO validation cluster fails after
enabling `TechPreviewNoUpgrade` because Cluster Version Operator cannot apply a
TechPreview-gated custom resource before its CRD is served.

This is the same CR-before-CRD payload/CVO ordering failure previously captured
for 4.22.0-rc.3 in `issues/2026-05-08.md`, reproduced here on **4.22.0-rc.5**.

## Primary failure

`ClusterVersion` reports:

```text
Could not update criocredentialproviderconfig "cluster" (33 of 1084):
the server does not recognize this resource, check extension API servers
```

The full `Failing` condition reason is `UpdatePayloadResourceTypeMissing`, and
the CVO log confirms the underlying discovery failure:

```text
error running apply for criocredentialproviderconfig "cluster" (33 of 1084):
failed to get resource type: no matches for kind "CRIOCredentialProviderConfig"
in version "config.openshift.io/v1alpha1"
```

The three TechPreview extension CRDs expected by `scripts/03-techpreview-setup.sh`
are absent:

```text
Error from server (NotFound): customresourcedefinitions.apiextensions.k8s.io "criocredentialproviderconfigs.config.openshift.io" not found
Error from server (NotFound): customresourcedefinitions.apiextensions.k8s.io "dnsnameresolvers.network.openshift.io" not found
Error from server (NotFound): customresourcedefinitions.apiextensions.k8s.io "osimagestreams.machineconfiguration.openshift.io" not found
```

## Payload evidence

The 4.22.0-rc.5 payload contains both the CR and CRD, but the CR sorts earlier
in the payload than the CRD:

```text
# 0000_05_config-operator_02_criocredentialproviderconfig.cr.yaml
apiVersion: config.openshift.io/v1alpha1
kind: CRIOCredentialProviderConfig
metadata:
  name: cluster
  annotations:
    release.openshift.io/create-only: "true"
    release.openshift.io/feature-gate: "CRIOCredentialProviderConfig"
```

```text
# 0000_10_config-operator_01_criocredentialproviderconfigs.crd.yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  annotations:
    api.openshift.io/merged-by-featuregates: "true"
    release.openshift.io/feature-set: CustomNoUpgrade,DevPreviewNoUpgrade,TechPreviewNoUpgrade
  name: criocredentialproviderconfigs.config.openshift.io
spec:
  group: config.openshift.io
  names:
    kind: CRIOCredentialProviderConfig
```

Because `TechPreviewNoUpgrade` enables the `CRIOCredentialProviderConfig`
feature gate, CVO selects the CR, reaches it as item `33 of 1084`, and stops
before reaching the CRD that would serve the API.

## Secondary rollout issue

After the initial CVO failure, additional ClusterOperators became degraded while
continuing to roll out control-plane payload content:

- `kube-apiserver`
- `kube-controller-manager`
- `kube-scheduler`

Their installer pods are stuck on `<master-0>` with the same
pod sandbox error:

```text
Failed to create pod sandbox: rpc error: code = Unknown desc = failed to create
pod network sandbox ...: no CNI configuration file in /etc/kubernetes/cni/net.d/.
Has your network provider started?
```

`<master-0>` itself remains `Ready`, `machineconfiguration.openshift.io/state=Done`,
and the `master` MCP reports `Updated=True`. This is a secondary rollout blocker
observed after the CVO failure; its causal relationship to the TechPreview
extension API/CRD failure was not confirmed. The first hard blocker remains the
CVO `CRIOCredentialProviderConfig` API type discovery failure.

## Current state

- `ClusterVersion`: `Available=True`, `Progressing=True`; `Failing` flaps when
  CVO retries item `33 of 1084`.
- `featuregate/cluster.spec.featureSet=TechPreviewNoUpgrade` is set and is
  irreversible.
- Required TechPreview CRDs are not present.
- Control-plane rollout is also blocked on `<master-0>` pod sandbox creation due
  to missing CNI configuration.
- Phases after `make techpreview` should not proceed on this cluster.

## Manual interventions taken

None. I did not hand-apply missing CRDs or otherwise work around the validation
failure.

## Verdict

This is a product/payload/CVO ordering issue in 4.22.0-rc.5. The validation repo
should continue to stop and document this condition rather than working around
it by manually applying the missing CRDs.

The existing known-bad TechPreview payload guard currently blocks 4.22.0-rc.3
and older pre-release payloads. This reproduction shows that 4.22.0-rc.5 also
has the same failure mode.
