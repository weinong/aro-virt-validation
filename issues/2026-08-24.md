# 2026-08-24 — TechPreviewNoUpgrade blocks on OCP 4.22.4: `CRIOCredentialProviderConfig` CR ordered before its CRD

## Summary

Enabling `TechPreviewNoUpgrade` on a freshly-upgraded **OCP 4.22.4** ARO cluster
puts `ClusterVersion` into a permanent `Failing`/`Progressing` state. The Cluster
Version Operator (CVO) cannot apply the `criocredentialproviderconfig/cluster`
custom resource because its CRD is never served:

```
Failing=True UpdatePayloadResourceTypeMissing:
  Could not update criocredentialproviderconfig "cluster" (33 of 1085):
  the server does not recognize this resource, check extension API servers
Progressing=True UpdatePayloadResourceTypeMissing:
  Unable to apply 4.22.4: a required extension is not available to update
```

This is a **payload manifest ordering bug**: the CR sorts before its own CRD, so
under TechPreview the CVO applies the CR first, fails, and never advances to the
manifest that creates the CRD.

Red Hat tracks this as a known defect: **[OCPBUGS-99266](https://redhat.atlassian.net/browse/OCPBUGS-99266)**.

This blocks the entire MSHV/CNV validation path (Phase 3 `techpreview` onward,
including the new day-2 RHCOS kernel-layering work, which requires TechPreview +
the `mshv` MachineConfigPool). The flow now **auto-remediates** this specific
defect (see "Automated workaround" below); the underlying payload bug remains
open.

## Root cause

`CRIOCredentialProviderConfig` is a TechPreview feature gate (confirmed enabled
in `featuregate/cluster` `status.featureGates[].enabled`). Extracting the 4.22.4
release payload (`oc adm release extract`) shows two config-operator manifests
whose CVO run order is inverted:

| CVO order (filename) | Object |
| --- | --- |
| `0000_05_config-operator_02_criocredentialproviderconfig.cr.yaml` | the **CR** `CRIOCredentialProviderConfig/cluster` |
| `0000_10_config-operator_01_criocredentialproviderconfigs.crd.yaml` | the **CRD** `criocredentialproviderconfigs.config.openshift.io` |

The CVO applies manifests in lexical filename order. `0000_05_…` (the CR) is
applied before `0000_10_…` (the CRD). Manifest annotations confirm both are
active under TechPreview:

- CR (`config.openshift.io/v1alpha1`, `kind: CRIOCredentialProviderConfig`,
  `name: cluster`) carries `release.openshift.io/feature-gate: "CRIOCredentialProviderConfig"`
  and `release.openshift.io/create-only: "true"`.
- CRD carries `release.openshift.io/feature-set: CustomNoUpgrade,DevPreviewNoUpgrade,TechPreviewNoUpgrade`.

Because the CR is `create-only` and gated on the feature (not the feature-set),
enabling TechPreview makes the CVO attempt the CR at run level `0000_05` while
its CRD only exists at run level `0000_10`. The CVO stops at manifest 33 of 1085
and never reaches the CRD, so the CRD is never created:

```
$ oc get crd criocredentialproviderconfigs.config.openshift.io
Error from server (NotFound): ... not found
$ oc api-resources | grep -i criocred   # (nothing)
```

`config-operator` itself reports `Available=True / Degraded=False` at 4.22.4 — it
does not reconcile this CRD independently of the CVO payload, so nothing else
heals it.

### A second instance in the same payload

Scanning the whole 4.22.4 payload for the same pattern (a feature-gated CR whose
manifest sorts before its CRD) finds a second latent occurrence that would wedge
the CVO next, once past `CRIOCredentialProviderConfig`:

| CVO order (filename) | Object |
| --- | --- |
| `0000_30_cluster-api-installer_06_clusterapi.yaml` | the **CR** `ClusterAPI` (`operator.openshift.io/v1alpha1`, gate `ClusterAPIMachineManagement`) |
| `0000_30_cluster-api_01_clusterapis.crd.yaml` | the **CRD** `clusterapis.operator.openshift.io` |

The CR filename sorts before the CRD filename (`cluster-api-installer` `-` `0x2d`
sorts before `cluster-api_` `_` `0x5f`), and both CRDs were confirmed missing on
the wedged cluster.

## Relationship to the existing known-bad-payload guard

`scripts/env.sh` (`is_known_bad_techpreview_payload`) only blocks
`4.22.0-ec.*` and `4.22.0-rc.<=3` for exactly this class of "CR before CRD"
failure. **4.22.4 (GA z-stream) is not covered and reproduces the same failure
for `CRIOCredentialProviderConfig`.** The guard's assumption that the issue was
limited to early 4.22 pre-release payloads is too narrow.

## Impact

- `ClusterVersion` is stuck `Failing=True`/`Progressing=True`; the cluster stays
  `Available=True` (workloads run) but the payload never fully applies.
- `scripts/03-techpreview-setup.sh` fails waiting for the CVO to settle, so
  `make aro-validation-flow` halts before Phase 4.
- Downstream MSHV/CNV steps (`scripts/04` requires `Progressing!=True` and
  `Failing!=True`; `rhel-10` OS stream; the new
  `scripts/12-rhcos-kernel-layer.sh`) cannot run.

## Automated workaround (in-flow, explicit band-aid)

Tracked upstream as [OCPBUGS-99266](https://redhat.atlassian.net/browse/OCPBUGS-99266).
Because this is a known Red Hat defect with no cluster-side declarative fix, the
flow now auto-remediates it instead of failing:

- `scripts/03a-payload-crd-ordering-fix.sh` extracts the running cluster's
  release payload, detects every feature-gated CR whose manifest sorts before its
  own CRD, and pre-applies the affected CRD(s) **verbatim from the payload** (it
  does not hand-author manifests). It skips CRDs already present and only applies
  under `TechPreviewNoUpgrade`.
- `scripts/03-techpreview-setup.sh` calls `03a` right after enabling
  `TechPreviewNoUpgrade`, and re-invokes it if the CVO reports
  `UpdatePayloadResourceTypeMissing` while settling.
- The version-based `guard_known_bad_techpreview_payload` check in Phase 3 was
  downgraded from fatal to informational, since detection is now payload-driven
  rather than a version blocklist.

Verified on this cluster: applying the two payload CRDs
(`criocredentialproviderconfigs.config.openshift.io`,
`clusterapis.operator.openshift.io`) cleared the wedge — `Failing` went
`True -> False` and the CVO resumed (`33 -> 160+ of 1085`).

This is a **band-aid, not a fix.** It unsticks the validation flow but does not
change the defective payload; the CVO still "owns" these CRDs and will reconcile
them at their (mis-ordered) run levels.

## Status / next steps

- **Open — tracked as [OCPBUGS-99266](https://redhat.atlassian.net/browse/OCPBUGS-99266).**
  Root cause is a release-payload manifest ordering bug: feature-gated CRs
  (`CRIOCredentialProviderConfig`, `ClusterAPI`) have run levels that precede
  their CRDs. The real fix belongs in the payload (order each CRD before its CR).
- The repo now applies the missing payload CRDs automatically as an explicit,
  documented workaround (`scripts/03a-payload-crd-ordering-fix.sh`). This is the
  one sanctioned exception to the README's "Manually applying missing payload
  CRDs" caution: it is automated, sourced from the payload, and tied to this
  open bug — remove it once a fixed 4.22.z payload is available.
- Re-test on a later 4.22.z payload where the manifest ordering is corrected and
  drop the workaround call from Phase 3 when OCPBUGS-99266 is resolved.
