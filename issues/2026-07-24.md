# 2026-07-24 - Diagnostic virt-launcher QEMU experiments

## Summary

A diagnostic hybrid virt-launcher image was built from the current CNV
virt-launcher while adding the complete QEMU userspace filesystem from upstream
KubeVirt `v1.8.2` under `/opt/qemu-upstream`. The CNV QEMU, libvirt, KubeVirt
binaries, configuration, and image entrypoint remain unchanged.

The upstream QEMU was executed directly on the current RHCOS 10 MSHV node. It
reproduced the shipped QEMU failure exactly:

```text
invalid intercept access type: execute
failed to handle mmio
Failed to run on vcpu 0
SIGABRT / exit 134
```

Both QEMU builds remain alive when started with `-S`, confirming that the
failure still begins when the MSHV vCPU executes.

Because the upstream candidate did not improve the direct-QEMU result, the
higher-risk OLM-managed `VIRT_LAUNCHER_IMAGE` override was not performed.

## Image Design

The hybrid keeps the original CNV paths intact, including:

```text
/usr/bin/virt-launcher
/usr/bin/virt-launcher-monitor
/usr/libexec/qemu-kvm
/usr/lib64/libvirt*.so*
```

Upstream QEMU is installed under a private prefix:

```text
/opt/qemu-upstream/rootfs/usr/libexec/qemu-kvm
/opt/qemu-upstream/rootfs/usr/lib64/
/opt/qemu-upstream/rootfs/usr/lib64/qemu-kvm/
/opt/qemu-upstream/rootfs/usr/share/qemu-kvm/
/opt/qemu-upstream/rootfs/usr/share/qemu/
/opt/qemu-upstream/rootfs/usr/share/OVMF/
/opt/qemu-upstream/rootfs/usr/share/edk2/
/opt/qemu-upstream/rootfs/usr/share/seabios/
/opt/qemu-upstream/rootfs/usr/share/seavgabios/
/opt/qemu-upstream/rootfs/usr/share/ipxe/
```

The wrapper `/opt/qemu-upstream/bin/qemu-kvm` invokes the copied upstream
dynamic loader with the copied upstream library directory and sets the QEMU
module/data paths. Runtime `/proc/<pid>/maps` verification showed libraries
loaded from the private upstream prefix rather than CNV `/usr/lib64`.

restricted temporary pod requesting only:


All probes used the same current node, kernel, `/dev/mshv`, and MSHV device

## Conclusion

Replacing the shipped QEMU `10.1.0-17.el9_8` with the upstream KubeVirt
`v1.8.2` QEMU `10.1.0-10.el9` does not change the failure on the current host
and kernel. This candidate therefore does not justify overriding the
OLM-managed virt-launcher image for full VMI testing.

This does not prove every upstream QEMU revision will fail. The branch tooling
supports overriding the upstream launcher digest so newer candidate builds can
be tested with the same private-sysroot and direct-MSHV controls before any
operator-level experiment.

## Manual Diagnostic Interventions

- Built and pushed a custom hybrid OCI image.
- Created one temporary namespace-scoped registry secret.
- Created one restricted diagnostic pod requesting the MSHV device.
- Ran direct QEMU commands outside KubeVirt/libvirt lifecycle control.
- The initial probes allowed QEMU core dumps and left host-managed
  `systemd-coredump` entries; the finalized smoke script sets `ulimit -c 0` to
  avoid creating additional persistent node artifacts. The original validation
  Job continued launching crashing VMIs concurrently, so node-wide coredump
  counts could not independently verify the smoke probes' suppression.
- Deleted the diagnostic namespace, secret, and pod after the probes.

No HCO, KubeVirt, CSV, Subscription, virt-operator, global pull secret, node,
MachineSet, or validation test resource was modified.

### Restoration

The diagnostic VMI, namespace, and temporary pull secrets were deleted. The
CSV and Deployment were restored to the shipped launcher digest. Rollback was
considered complete only after KubeVirt's target and observed deployment
configs and the virt-handler init image all converged to:

```text
quay.io/openshift-cnv/container-native-virtualization-virt-launcher-rhel9@sha256:8b2448f9ba5b37c21e908d1c1f1a9575741ee22054d3a00bcd03f21af4fee2b3
```

The successful diagnostic does not make the custom launcher a product fix.
The normal CNV-delivered image remains unchanged and the underlying issue stays
open until CNV delivers the corrected QEMU build.

### Persistent validation option

The branch adds an opt-in `USE_QEMU_3_LAUNCHER=true` validation path. It
configures the digest-pinned `.3` launcher and HCO-managed registry pull secret,
waits for the image holder and virt-handler to converge, then invokes the
existing validation checkup without changing its suites or filters.

Per the requested test workflow, this path does not restore the original
launcher when validation completes, fails, or reaches its local wait timeout.
The in-cluster Job can continue naturally with the `.3` launcher. Restoration
is a separate explicit command and is guarded by cluster, resource UID,
resource-version, applied-image, HCO-patch, and secret-ownership checks.
