# 2026-07-02 - Exact OCP 4.22.4 target unavailable for pinned ARO validation flow

## Summary

The pinned ARO validation flow was run from a fresh ARO cluster and stopped before
TechPreview, MSHV node setup, CNV installation, HCO patching, and validation
checkup because exact OCP `4.22.4` is not currently available in the cluster
update graph or public `4.22` update channels.

The flow is intentionally pinned to `4.22.4`; it did not fall back to `4.22.3`
or any other `4.22.z` payload.

## Reproduction Flow

The run started with:

```sh
TARGET_OCP_VERSION=4.22.4 make aro-validation-flow
```

The first attempt created the ARO cluster, logged in, disabled ARO MachineSet
reconciliation, and then hit a local automation issue in the ARO API URL
comparison. Commit `b051a27` corrected only that local script comparison by
normalizing trailing slashes before comparing the `oc` API server and Azure ARO
API server values. This did not affect or resolve the unavailable `4.22.4`
target.

The flow was then resumed against the existing cluster in `.aro.env`:

```sh
make aro-login \
  && make aro-disable-machineset-reconcile \
  && make upgrade-to-4.22.4 \
  && make techpreview \
  && make mshv-node \
  && make cnv-pull-secret \
  && make cnv-install \
  && make mshv-hco-patch \
  && make validation-checkup
```

The `4.20.15` -> `4.21.22` hop completed successfully. The next pinned hop to
exact `4.22.4` failed during target selection.

```text
Exact target 4.22.4 not found in cluster's available/conditional updates.
Querying Red Hat update graph API for candidate-4.22...
Exact target 4.22.4 was not found in cluster updates or candidate-4.22 graph.
This flow is pinned and will not fall back to another 4.22.x version.
```

## Required Setup Action

ARO MachineSet reconciliation was explicitly disabled after cluster creation:

```sh
oc patch cluster.aro.openshift.io cluster --type=merge \
  -p '{"spec":{"operatorflags":{"aro.machineset.enabled":"false"}}}'
```

This is required by the repo instructions before creating custom MSHV
MachineSets on recreated ARO clusters. It is not a fix for the unavailable
`4.22.4` target.

## Local Automation Correction

The first flow attempt exposed a local script comparison issue: Azure returned
the ARO API URL with a trailing slash while `oc whoami --show-server` omitted
it. Commit `b051a27` normalized those URLs and the flow was resumed against the
same cluster.

This was a local automation correction only. It did not change the cluster
payload, did not provide a `4.22.4` image, and did not mitigate the reported
validation blocker.

## Manual Interventions and Workarounds

No product payload, missing CRDs, node labels, MachineSets, or validation test
results were manually altered or worked around.

## Impact

The requested pinned end-to-end validation cannot proceed until exact OCP
`4.22.4` is present in an update graph or a verified release image is provided.

Blocked phases:

1. Upgrade to exact OCP `4.22.4`.
2. `TechPreviewNoUpgrade` enablement on the requested target.
3. MSHV node creation.
4. CNV/OpenShift Virtualization installation.
5. HCO `hyperv-direct` patching.
6. `ocp-virt-validation-checkup` execution.

## Next Steps

1. Retry the pinned flow when `4.22.4` appears in `candidate-4.22`, `fast-4.22`,
   or another approved graph/source.
2. If a specific `4.22.4` release image is expected but not graph-published,
   provide that exact digest and add an explicit, reviewed `--to-image` path for
   the pinned target.
3. Do not fall back to `4.22.3` unless the validation requirement changes.
