# 2026-08-31 — CNV `virt-platform-autopilot` KubeletConfig takes MSHV + worker nodes NotReady

## Summary

Installing OpenShift Virtualization (CNV nightly `4.99.0-2967`) on this ARO
cluster deployed a new component, **`virt-platform-autopilot` (v1.0.0)**, which
automatically created a cluster `KubeletConfig` (`virt-cpu-manager`) and a
`MachineConfig` (`90-worker-swap-online`) targeting the **worker** MachineConfig
pool. The mshv MachineConfigPool inherits worker MachineConfigs (its nodes carry
the `worker` role), so both pools rolled the change out. The first node of each
pool to reboot into the new config — the MSHV node
(`Standard_D192ds_v6`, multi-NUMA) and a regular worker
(`Standard_D8s_v5`) — came up with **kubelet down** and went `NotReady`
(`kubelet stopped posting node status`, port 10250 refused). They do not
self-recover.

The most likely trigger is the autopilot's KubeletConfig:

```yaml
cpuManagerPolicy: static
cpuManagerPolicyOptions: {full-pcpus-only: "true"}
memoryManagerPolicy: Static
reservedMemory:
- numaNode: 0
  limits: {memory: 1124Mi}
reservedSystemCPUs: 0-1
topologyManagerPolicy: best-effort
```

`memoryManagerPolicy: Static` requires `reservedMemory` entries for **every**
NUMA node; this config only covers NUMA node 0, which makes kubelet fail to
start on multi-NUMA nodes (the `Standard_D192ds_v6` MSHV node has many NUMA
nodes). A regular `Standard_D8s_v5` worker was also taken down when it rolled
the same config.

## Environment

- ARO 4.22.4, cluster `aro-virt-test`, RG `aro-virt-test-rg-o98l`, managed RG `aro-wa2fvt52`.
- CNV nightly CSV `kubevirt-hyperconverged-operator.4.99.0-2967`.
- Component: Deployment `openshift-cnv/virt-platform-autopilot`, image label
  `platform.kubevirt.io/managed-by: virt-platform-autopilot`, `platform.kubevirt.io/version: 1.0.0`.
- Affected nodes:
  - `aro-virt-test-8gpzs-worker-mshv-centralus1-6rjd2` (`Standard_D192ds_v6`, roles `mshv,worker`) — NotReady.
  - `aro-virt-test-8gpzs-worker-centralus1-qv7ct` (`Standard_D8s_v5`, role `worker`) — NotReady.
  - `centralus2`/`centralus3` workers stayed `Ready` on the prior config (pool rolls one node at a time).

## Objects the autopilot created

```
KubeletConfig/virt-cpu-manager        (label managed-by=virt-platform-autopilot, mcpSelector: pools...worker="")
MachineConfig/90-worker-swap-online   (label managed-by=virt-platform-autopilot; swap-file enable + watermark tuning)
```

`KubeletConfig/virt-cpu-manager` has no `ownerReferences`; the autopilot
Deployment is owned by the CSV (non-controller ref). There is **no HCO field or
feature gate** to disable the autopilot (`spec.featureGates` is empty; the
deployment has no disable flag), and the CSV install strategy pins the
deployment to `replicas: 1`, so OLM reconciles it back after a manual scale-down.

## Impact

- Two nodes down (the only MSHV node + one worker); `worker` and `mshv` MCPs
  stuck `Updating`.
- Blocks the MSHV/L1VH validation: no schedulable MSHV node, `virt-handler`
  cannot run there, and `scripts/07-mshv-hco-patch.sh` fails its virt-handler
  readiness check.
- Node recovery requires recreation (kubelet is down and cannot apply a rolled-
  back config), and any recreated node is re-broken while the autopilot is
  running because it re-creates the same KubeletConfig for the worker pool.

## Manual interventions performed (NOT a fix — issue stays open)

These were required to stop the bleeding; they are explicit manual workarounds,
not a product fix:

1. `oc scale deploy virt-platform-autopilot -n openshift-cnv --replicas=0`
   — stop the autopilot from re-creating the configs. **OLM reverts this** to
   `replicas=1` per the CSV install strategy, so it is not durable on its own.
2. `oc delete kubeletconfig virt-cpu-manager`
3. `oc delete machineconfig 90-worker-swap-online`

Still required to recover (pending, see next steps): a durable way to keep the
autopilot from re-creating the KubeletConfig, then recreate the two NotReady
Machines so the MachineSets provision clean nodes (the mshv node re-applies the
L1VH `osImageURL` layer on reboot).

## Next steps

- Engage Red Hat/CNV: `virt-platform-autopilot` must not emit a
  `memoryManagerPolicy: Static` KubeletConfig with `reservedMemory` for only one
  NUMA node, and must not blanket-target MSHV/multi-NUMA worker nodes. Provide a
  supported opt-out.
- Determine the supported way to disable the autopilot (HCO annotation/feature
  gate) rather than scaling the OLM-managed deployment.
- Recreate the two NotReady nodes once the autopilot is durably disabled.
