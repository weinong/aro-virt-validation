# 2026-08-31 — CNV `virt-platform-autopilot` KubeletConfig takes MSHV + worker nodes NotReady

## Summary

Installing OpenShift Virtualization (CNV nightly `4.99.0-2967`) on this ARO
cluster deployed a new component, **`virt-platform-autopilot` (v1.0.0)**, which
automatically created a cluster `KubeletConfig` (`virt-cpu-manager`) and a
`MachineConfig` (`90-worker-swap-online`) targeting the **worker** MachineConfig
pool. The mshv MachineConfigPool inherits worker MachineConfigs (its nodes carry
the `worker` role), so both pools rolled the change out. The first node of each
pool to reboot into the new config — the MSHV node
(`Standard_D192ds_v6`) and a regular worker
(`Standard_D8s_v5`) — came up with **kubelet down** and went `NotReady`
(`kubelet stopped posting node status`, port 10250 refused). They do not
self-recover.

The trigger is the autopilot's KubeletConfig (root cause confirmed below — a
memory-manager/Node-Allocatable mismatch that fails on any node, not a
NUMA-specific issue):

```yaml
cpuManagerPolicy: static
cpuManagerPolicyOptions: {full-pcpus-only: "true"}
memoryManagerPolicy: Static
reservedMemory:
- numaNode: 0
  limits: {memory: 1124Mi}
reservedSystemCPUs: 0-1
topologyManagerPolicy: best-effort
```

## Confirmed root cause (reproduced)

The failure is a **kubelet memory-manager (Static policy) Node-Allocatable
validation error**, and it is deterministic on **any** node (single- or
multi-NUMA) — which is why both the multi-NUMA D192 mshv node and a single-NUMA
D8 worker went down. Reproduced by running the kubelet binary (v1.35.5) against
the exact autopilot KubeletConfig on a healthy single-NUMA worker (throwaway
`--root-dir`, so the live kubelet was untouched):

```
E kubelet container_manager_linux.go:357] "Failed to initialize memory manager"
  err="the total amount \"1124Mi\" of type \"memory\" is not equal to the value \"100Mi\" determined by Node Allocatable feature"
E kubelet run.go:72] "command failed"
  err="failed to run Kubelet: the total amount \"1124Mi\" of type \"memory\" is not equal to the value \"100Mi\" determined by Node Allocatable feature"
```

Why: the Static memory manager requires

```
sum(reservedMemory[*].limits.memory)  ==  systemReserved.memory + kubeReserved.memory + evictionHard.memory.available
```

The autopilot config declares `reservedMemory = 1124Mi` but sets **no**
`kubeReserved.memory` and **no** `systemReserved.memory` (its `kubeReserved.cpu`
is even overwritten by `reservedSystemCPUs`). The only memory reserved via Node
Allocatable is the default hard-eviction threshold `memory.available: 100Mi`.
So kubelet computes `1124Mi != 100Mi` and refuses to start.

**This is a `virt-platform-autopilot` bug (file with the CNV team), not a kernel
or kubelet bug.** Kubelet is correctly rejecting an internally-inconsistent
config. The autopilot must emit a matching `kubeReserved.memory`/
`systemReserved.memory` (totalling its `reservedMemory`, here 1124Mi), or not set
`reservedMemory` beyond what it reserves.

### Reproduction (any RHCOS worker, non-destructive)

```sh
# On a Ready node via `oc debug node/<worker> -- chroot /host`:
cat > /tmp/kc.yaml <<'YAML'
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
cpuManagerPolicy: static
cpuManagerPolicyOptions: {full-pcpus-only: "true"}
memoryManagerPolicy: Static
reservedMemory:
- {numaNode: 0, limits: {memory: 1124Mi}}
reservedSystemCPUs: "0-1"
kubeReserved: {cpu: "1"}
YAML
timeout 25 kubelet --config=/tmp/kc.yaml --root-dir=/tmp/klrepro \
  --kubeconfig=/var/lib/kubelet/kubeconfig \
  --container-runtime-endpoint=unix:///var/run/crio/crio.sock \
  --register-node=false --hostname-override=klrepro-probe
# -> "Failed to initialize memory manager: the total amount 1124Mi of type
#     memory is not equal to the value 100Mi determined by Node Allocatable feature"
```

Node facts observed: kubelet `v1.35.5`; the D8 worker is single-NUMA
(`NUMA node(s): 1`) with pre-existing `cpu_manager_state` policy `none` and
`memory_manager_state` policy `None`. The mismatch above fires in
`NewContainerManager` (before serving), independent of NUMA count or the
existing checkpoints.

## Environment

- ARO 4.22.4, cluster `aro-virt-test`, RG `aro-virt-test-rg-o98l`, managed RG `aro-wa2fvt52`.
- CNV nightly CSV `kubevirt-hyperconverged-operator.4.99.0-2967`.
- Component: Deployment `openshift-cnv/virt-platform-autopilot`, image label
  `platform.kubevirt.io/managed-by: virt-platform-autopilot`, `platform.kubevirt.io/version: 1.0.0`.
- Affected nodes:
  - `aro-virt-test-8gpzs-worker-mshv-centralus1-6rjd2` (`Standard_D192ds_v6`, roles `mshv,worker`) — NotReady.
  - `aro-virt-test-8gpzs-worker-centralus1-qv7ct` (`Standard_D8s_v5`, role `worker`) — NotReady.
  - `centralus2`/`centralus3` workers stayed `Ready` on the prior config (pool rolls one node at a time).

## Objects the autopilot created

```
KubeletConfig/virt-cpu-manager        (label managed-by=virt-platform-autopilot, mcpSelector: pools...worker="")
MachineConfig/90-worker-swap-online   (label managed-by=virt-platform-autopilot; swap-file enable + watermark tuning)
```

`KubeletConfig/virt-cpu-manager` has no `ownerReferences`; the autopilot
Deployment is owned by the CSV (non-controller ref). There is **no HCO field or
feature gate** to disable the autopilot (`spec.featureGates` is empty; the
deployment has no disable flag), and the CSV install strategy pins the
deployment to `replicas: 1`, so OLM reconciles it back after a manual scale-down.

## Impact

- Two nodes down (the only MSHV node + one worker); `worker` and `mshv` MCPs
  stuck `Updating`.
- Blocks the MSHV/L1VH validation: no schedulable MSHV node, `virt-handler`
  cannot run there, and `scripts/07-mshv-hco-patch.sh` fails its virt-handler
  readiness check.
- Node recovery requires recreation (kubelet is down and cannot apply a rolled-
  back config), and any recreated node is re-broken while the autopilot is
  running because it re-creates the same KubeletConfig for the worker pool.

## Manual interventions performed (NOT a fix — issue stays open)

These were required to stop the bleeding; they are explicit manual workarounds,
not a product fix:

1. `oc scale deploy virt-platform-autopilot -n openshift-cnv --replicas=0`
   — stop the autopilot from re-creating the configs. **OLM reverts this** to
   `replicas=1` per the CSV install strategy, so it is not durable on its own.
2. `oc delete kubeletconfig virt-cpu-manager`
3. `oc delete machineconfig 90-worker-swap-online`

## Supported mitigation (applied)

The autopilot (Dev Preview, [openshift-virtualization/virt-platform-autopilot](https://github.com/openshift-virtualization/virt-platform-autopilot),
[Red Hat Developer intro](https://developers.redhat.com/articles/2025/introducing-virtualization-platform-autopilot))
documents Day-0 opt-out annotations on the HyperConverged CR. We use
`platform.kubevirt.io/disabled-resources` to exclude the two breaking resources,
which is the supported way to keep the autopilot running while preventing it from
creating the invalid KubeletConfig and swap MachineConfig:

```sh
oc annotate hco kubevirt-hyperconverged -n openshift-cnv \
  'platform.kubevirt.io/disabled-resources=- kind: KubeletConfig
  name: virt-cpu-manager
- kind: MachineConfig
  name: 90-worker-swap-online'
oc scale deploy virt-platform-autopilot -n openshift-cnv --replicas=1   # back to supported state
```

Verified: with the annotation set and the autopilot re-enabled, its dry-run
`/debug/render` no longer contains `virt-cpu-manager`/`memoryManager`/swap, and it
reports `Reconciliation succeeded: 0/5 assets applied` (everything else is
soft-dependency-skipped on this cluster). Healthy workers stayed `Ready`.

This mitigation is baked into `scripts/06-cnv-install.sh` (the HyperConverged CR
is created with the `disabled-resources` annotation), so fresh installs never
create the broken resources. **Note:** the "not a worker" idea does not help —
the mshv pool must inherit the ~12 worker base MachineConfigs (kubelet, cri-o,
ARO DNS/registries, etc.) to function, and the autopilot breaks plain worker
nodes too, so isolating mshv would not have prevented the outage.

Still required to recover: recreate the two NotReady Machines so the MachineSets
provision clean nodes (the mshv node re-applies the L1VH `osImageURL` layer on
reboot). The underlying autopilot bug stays open pending a CNV fix.

## Note on node access

The exact error above was obtained by **reproducing** the config with the
kubelet binary on a healthy worker (see reproduction), because ARO applies a
deny assignment on the managed RG that blocks both `az vm run-command` and
`az vm boot-diagnostics ...` (`DenyAssignmentAuthorizationFailed`), so the
journal on the down nodes themselves is not directly reachable.

## Next steps

- Engage Red Hat/CNV: `virt-platform-autopilot` emits a `memoryManagerPolicy:
  Static` KubeletConfig whose `reservedMemory` (1124Mi) does not match the
  configured `kubeReserved`/`systemReserved` memory (effectively 100Mi via the
  default eviction threshold), so kubelet fails Node-Allocatable validation and
  will not start on any node. The autopilot must set matching
  `kubeReserved.memory`/`systemReserved.memory`, and should not blanket-target
  MSHV worker-role nodes. Kubelet and the RHCOS/L1VH kernel are not at fault.
- Supported opt-out is in place (`platform.kubevirt.io/disabled-resources` on the
  HCO, baked into `scripts/06-cnv-install.sh`); remove it once the autopilot bug
  is fixed.
- Recreate the two NotReady nodes (clean config now that the invalid resources
  are excluded).
